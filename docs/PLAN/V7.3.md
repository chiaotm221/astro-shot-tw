# V7.3 — Live Mobile Pointing Mode

## Status

Researched and planned, but implementation is intentionally blocked until the
V7.2 EXIF completion gate passes. No live-sensor code should be added before
then.

## Objective

Let a user point a phone toward the sky and use the device's orientation
sensors to set the simulator azimuth and camera tilt. This provides a live
composition aid similar to mobile planetarium apps; it does not claim survey-
grade heading or telescope-pointing accuracy.

## Browser APIs

- Prefer the secure-context `deviceorientationabsolute` event when absolute
  orientation is available.
- Fall back to `deviceorientation` only when its `absolute` flag or a browser-
  specific compass heading provides a usable north reference.
- On browsers exposing `DeviceOrientationEvent.requestPermission`, request
  absolute orientation from a user-initiated button and handle granted, denied,
  unavailable, and no-data states separately.
- Support Safari's `webkitCompassHeading` and `webkitCompassAccuracy` as an
  explicit magnetic-north source rather than labeling it true north.
- Account for portrait and landscape screen rotation before mapping device
  coordinates to camera azimuth, pitch, and roll.

## User Flow

1. The user presses **Use phone direction**.
2. AstroShot explains that compass, accelerometer, and gyroscope access remains
   local, then requests browser permission.
3. A live indicator displays heading, tilt, north-reference type, reported
   accuracy, and sensor status.
4. The simulator follows the phone after a short calibration step.
5. The user can pause and lock the current direction before exporting a sky or
   star-trail image.
6. Manual azimuth and tilt remain available whenever sensors are absent,
   denied, unstable, or inaccurate.

## Processing Rules

- Convert the browser's alpha/beta/gamma rotation into a viewing quaternion or
  direction vector; do not treat beta alone as camera pitch.
- Compensate for `screen.orientation.angle` so portrait and landscape produce
  the same physical pointing direction.
- Smooth heading on the unit circle to avoid discontinuity at 0/360 degrees;
  smooth tilt separately with a short low-pass filter.
- Reject null values, non-finite values, implausible jumps, and stale events.
- Update React display state at low frequency while sending sensor samples to
  renderer refs at animation frequency.
- Never start sensor access automatically on page load.

## Accuracy and Calibration

- Display **true north**, **magnetic north**, or **relative only** according to
  the actual source.
- Do not silently convert magnetic north to true north in Phase 1.
- Warn when Safari reports poor `webkitCompassAccuracy`, when absolute heading
  is unavailable, or when samples are disturbed by nearby metal or magnets.
- Provide a zero/align control so the user can correct a consistent heading or
  mounting offset against a known direction.
- Treat the output as composition guidance; the final lock remains a user-
  confirmed direction.

## Phase 1 Scope

- Permission and feature-detection state machine.
- Live azimuth and tilt control in portrait and landscape orientations.
- Standard absolute-orientation path plus Safari compass fallback.
- Pause/lock, calibration offset, smoothing, and manual fallback.
- Local-only privacy disclosure and no sensor-data persistence by default.
- Unit tests for coordinate conversion, screen rotation, wrap-around smoothing,
  permission states, and invalid samples.
- Manual testing on at least one current iPhone Safari and one Android Chrome
  device over HTTPS.

## Non-Goals

- Native iOS or Android sensor APIs.
- Background sensor collection.
- Automatic image compositing or transmission to an AI provider.
- Survey, navigation, telescope control, or augmented-reality registration
  guarantees.
