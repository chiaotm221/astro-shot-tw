# V6.1 — Offline Data and Update Management

## Status

Phase 1 implemented. Static-export, source, and service-worker regression tests
are complete. Installed-app, real network-disconnection, quota-pressure, and
service-worker replacement checks remain pending because they require a
connected browser environment.

## Objective

Make offline availability understandable and controllable instead of leaving
service-worker state invisible to the user.

## Scope

- Add an offline-data panel showing application-shell readiness, star-data
  readiness, last refresh time, and approximate storage use when supported.
- Provide explicit actions to download or refresh offline data and remove
  AstroShot-managed caches.
- Detect a waiting service worker and offer a user-controlled update action.
- Explain that weather is external data and may be stale or unavailable.
- Preserve bundled and custom observing locations locally without introducing
  accounts or remote synchronization.
- Handle partial cache failures and retry only missing required resources.
- Add browser automation for first load, offline reload, base-path deployment,
  stale weather, and service-worker replacement.

## Constraints

- Cache deletion must target only AstroShot-owned cache names.
- An update must not interrupt an active photography or simulation session
  without explicit user action.
- Storage APIs must remain optional because browser support and quotas vary.
- The application must continue to work online if service-worker registration
  or cache storage fails.

## Acceptance Criteria

- A user can tell whether core offline data is ready before leaving coverage.
- A user can refresh or remove offline data without clearing all browser data.
- A waiting application update is visible and can be applied intentionally.
- Offline reload succeeds after a confirmed download on supported browsers.
- Partial download and quota failures produce actionable, localized feedback.
- Automated browser coverage exercises online-to-offline and update flows.

## Deferred

- Scheduled background synchronization.
- Push notifications.
- Downloadable regional terrain, weather, or map tile packages.
- Cross-device cache or location synchronization.

## Implementation Evidence

- The settings menu reports required core-asset and star-catalog readiness.
- Users can download, refresh, or remove only `astroshot-` managed caches.
- Storage estimates remain optional and are labeled as browser-wide usage.
- A waiting service worker is applied only after the user selects the update
  action, followed by a controller-change reload.
- The service worker retries missing assets, can force a refresh, and reports
  partial failures through a message channel.
- The service worker discovers hashed same-origin script and stylesheet URLs
  from the exported application entry point before writing a versioned
  readiness marker, so a first-load download cannot falsely report readiness.
- Root and configured base-path static exports remain supported.

## Remaining Browser Verification

- Install and launch in standalone mode on current Chromium and iOS Safari.
- Confirm an online first load can be reloaded after a real network disconnect.
- Confirm the update action replaces an older active service worker without
  interrupting the session before user consent.
- Exercise partial downloads and browser storage quota pressure.
